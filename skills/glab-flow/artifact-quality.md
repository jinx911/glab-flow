# 交付文档质量标准

glab-flow 的文档产物不是过程装饰，而是开发、测试、评审、发布的共同输入。高质量标准只有一个：下游能按文档行动，且不需要反复猜业务规则、技术边界、测试数据和发布风险。

三份核心文档职责必须分清：

| 文档 | 负责回答 | 不负责 |
|---|---|---|
| `proposal.md` | 为什么做、给谁用、做什么/不做什么、业务规则、权限、边界、验收标准 | 技术实现细节 |
| `design.md` | 怎么实现、为什么这样实现、影响哪些系统、如何迁移/回滚/观测 | 重复完整 PRD |
| `test-plan.md` | 每条 AC 怎么测、在哪个环境测、用什么数据、由哪个脚本/资产执行、产出什么证据 | 临场执行日志 |

## 通用质量门槛

- **可追溯**：需求目标 → AC → 设计点 → 测试 case → 测试数据/证据必须能串起来。
- **可判断**：避免“尽量、适当、相关、优化一下、保持一致”等模糊词；改写成明确条件、规则、阈值、提示语或验收方式。
- **可执行**：每个表、接口、字段、权限、配置、数据、脚本路径都必须落到具体对象；不能只写抽象描述。
- **有边界**：范围内、范围外、异常路径、权限变化、状态变化、历史数据兼容必须显式说明；不涉及也要写判断依据。
- **少重复**：Issue 公共评论写团队需要读的摘要；DU/本地目录保存执行明细；三份文档只写各自职责，不互相复制大段内容。
- **图表优先**：跨角色、跨系统、状态流转、异步链路和发布顺序优先用 Mermaid 图或表格，避免纯文字堆砌。
- **变更留痕**：已确认内容变化时走 `change-impact` / `change-close`，不靠文档内 changelog 私改需求。

## `proposal.md` 质量标准

`proposal.md` 是需求验收标准的权威来源。最低结构：

1. 需求背景与目标：业务痛点、影响对象、为什么现在做、可验证的业务结果。
2. 应用范围：Web/H5/iOS/Android/后端接口/定时任务/消息等是否涉及。
3. 用户范围与权限：角色定义、数据范围、操作权限矩阵。
4. 业务流程与状态：主流程图；状态流转表；触发条件与异常处理。
5. 功能详细说明：入口、触发条件、字段定义、校验规则、展示规则、交互反馈、提示语。
6. 边界条件与异常处理：空数据、超长内容、重复点击、并发、权限变化、状态已变、外部依赖失败。
7. 非功能需求：性能、安全/脱敏/越权、数据兼容、可用性、审计日志；只在命中时展开，不涉及写依据。
8. 埋点与统计：事件、触发时机、属性、用途；无需求写“不涉及 + 原因”。
9. 验收标准：每条使用 Given/When/Then，且可映射到测试 case。
10. 需求评审问题、裁定与改进建议：问题、推荐方案、用户/产品裁定、采纳项影响章节。

禁止：只复述 Issue 原文、只有功能清单、保留 TBD/TODO、把 P2 未来预留写进本次范围、没有边界/异常、没有可测试 AC。

## `design.md` 质量标准

`design.md` 是实现与评审的权威输入。最低结构：

1. 背景与目标摘要：从 `proposal.md` 摘要 Why/What，不重复完整 PRD；明确非目标。
2. 总体设计：方案概述、系统上下文/架构图、核心链路流程图/时序图。
3. 关键文件与改动：每个文件写“改什么、为什么、影响范围、关联 AC”。
4. 条件详细设计：
   - 存储/数据：表、字段、索引、migration、历史数据兼容、缓存 key/TTL/更新策略。
   - API/接口：endpoint、入参、出参、错误码、幂等、分页、鉴权。
   - 核心规则/状态机：复杂规则、审批、状态流转、异步任务、补偿。
   - 权限与安全：角色、菜单、数据权限、敏感字段、越权防控。
5. 非功能与风险：性能/容量、一致性/并发/幂等、兼容/迁移、降级/故障预案。
6. 可观测性：日志、指标、告警、排查入口；命中生产风险/异步/外部依赖/关键链路时必填。
7. 实施与发布方案：实施顺序、A/B 配置清单、发布顺序、回滚方案。
8. 测试策略输入：AC、风险点、建议测试方式、需要的数据。

命中跨系统调用、状态流转、异步链路、发布顺序时必须有 Mermaid 图；不命中时写“不涉及 + 依据”。禁止只列文件名、只贴伪代码、只写主流程、不写失败处理。

## `test-plan.md` 质量标准

`test-plan.md` 是 local/test 两道门禁的共同输入。最低结构：

1. 测试目标：对齐 `proposal.md` 业务目标和 `design.md` 技术风险。
2. 覆盖范围：范围内/范围外；范围外必须写理由。
3. AC → case → 风险映射：每条 AC 至少一个 case；每个设计风险至少一个验证手段。
4. 用例清单：case ID、标题、关联 AC、方法（unit/api/integration/e2e/script/data/manual）、环境、步骤、预期、证据类型。
5. 环境矩阵：local/test 的 webUrl、脚本 root、命令、env 文件、账号变量、数据库引用、数据前缀。
6. 场景 ↔ 数据映射：每个 case 在每个执行环境都有对应测试数据、关键业务键、来源、生命周期。
7. 前置条件与数据准备：fixture/seed、数据库回读、账号、权限、配置开关；进入执行前必须 E0 检查。
8. 边界与异常：空值、越界、非法输入、重复点击、并发、权限变化、状态已变、外部依赖失败、大数据量、特殊字符。
9. 执行入口：项目脚本或 E2E runner；禁止临场 curl/一次性脚本作为门禁证据。
10. 证据规则：TestRun、脚本报告、数据库回读、人工核对项如何产生和回读。

计划顶部必须包含唯一 `glab-flow:test-plan:v1` marker。计划实质变化必须递增 `plan-version`；旧 TestRun/ 自动失效。`test-plan.md` 不记录实际执行流水，执行事实进入 DU 和测试报告。
