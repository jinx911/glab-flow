# glab-flow 核心模型重设计：以交付工作包为中心

- 日期：2026-09-01
- 状态：已确认（用户逐节认可：核心模型 / 路线推导 / 流程图 / 完整设计）
- 前置讨论：用户对 glab-flow 提出 12 条高层反馈，确认按「重新设计核心模型」处理

## 1. 问题陈述（12 条反馈的归纳）

现行 glab-flow 以「状态机流转」为中心：节点流转是主语，交付物是流转的副产品。由此衍生出四类核心痛点：

1. **人工介入过多**：semi/full-auto 两档 + hard_gate 之外，所有动作挤在同一档确认里；一个「开发中→测试中」要过 5-6 个人工点（节点确认、Jenkins 逐参数、部署清单、preview、回读）。
2. **变化无分级**：change-impact 有 7 个影响维度，但全部走同一个 open→close 重闭环；plan-version 一变即双环境全量重测——改一行文案与改数据模型的代价相同。
3. **环境资源非一等模型**：分支、worktree、Apifox 资产、测试数据、报告、部署版本散落在 config/test-config 与各 sub-skill 约定里（如 `TMP-<iid>-` 前缀），靠约定和记忆串联，无生命周期管理。
4. **缺最短路径视图**：transition 输出 missing[]+hint 是门禁清单视角；用户看不到「当前在哪、阻塞什么、最快怎么继续、谁欠什么」。
5. **Issue 信息过载**：TestRun marker、AssetAudit、变更单、周排期、MR 评论全部进 Issue，一个需求几十条评论。
6. **门禁固定绑定每个转换**：所有需求走同样的全量门禁，简单需求（文案级）陪跑重流程。
7. **外部事实是异常而非常态**：人工发布、人工改标签、外部 CI 结果只能当「脏状态」处理，无导入-对账-继续的原语。
8. **证据偏存在性校验**：有报告/评论/版本 ≠ 真实通过；语义可信（覆盖范围、关联关系）未建模。
9. **扩展机制不足**：state-machine.yaml 是单一全局模型，项目间只能开关 config 字段，不能换分支策略/测试平台/审批要求。
10. **成功指标缺失**：只有合规审计（writebackAudit），无周期/介入次数/重复测试/返工率度量。

## 2. 设计目标与非目标

### 2.1 必须解决的核心目标（用户确认）

- G1 降人工介入次数（标准需求 ≤7 次确认，且全部是业务判断或硬门）
- G2 变化分级闭环（按影响维度推导验证深度，不再全量重测）
- G3 环境资源一等模型（显式注册 + 生命周期 + 终态清理）
- G4 最短路径视图（`next` 查询：在哪/阻塞/下一步/谁欠什么）

### 2.2 用户拍板的关键决定

| 决定 | 内容 |
|---|---|
| 铁律全保留 | GitLab Issue 唯一真相、引擎纯计算无 I/O、preview-confirm、评论不可变（G7/G8）、不建 Jira（G13） |
| 存量兼容 | 旧 Issue 接入时由回读对账自动推导 DU，不做双轨期，历史评论只读不迁移 |
| 范围 | 全量设计、分阶段实施 |
| 双档模型 | 内部以 DeliveryUnit 为主档，对外 labels 仍是 8 状态词汇表（story）/6 状态（bug），状态 = 投影 |
| Issue 评论策略 | **只在状态流转时发评论**；执行明细（TestRun/AssetAudit/变更单）降为 DU 本地事实 |
| 凭据划线 | 动作分层按「是否生产」划线，不按「是否敏感」：非生产账号/环境操作全 L1 |
| 路线机制 | 不设预设档位；技术方案声明受影响维度 → 引擎确定性推导 GateSet；棘轮只升不降，降级需显式 L2 改判留痕 |
| 变化分级 | 与路线推导是同一矩阵的两个时刻（设计时定初版、变更时增量扩容） |

### 2.3 非目标（本轮不做）

- 不更换持久层（Issue 仍是唯一真相，本地 state 仍是派生缓存）
- 不重设计对外状态词汇表
- 不引入流程插件市场式扩展机制（维度→门禁矩阵已覆盖主要扩展需求）
- 证据「语义可信」的深度建模（如覆盖度计算）留待后续迭代；本轮以证据摘要 + 指标先行

## 3. 核心模型：四层内核

```
DeliveryUnit（交付工作包）—— 唯一主档
  目标 / 产物清单 / 证据集 / 资源集 / 受影响维度 / GateSet
  承载：Issue 评论（流转时，结构化）+ 本地 state（派生缓存）
       │
       ├── ActionPolicy（动作分层）
       ├── GateSet（门禁集 = 维度推导）
       └── ResourceRegistry（资源登记表）
状态机 = 投影函数：DeliveryUnit × GateSet → labels
最短路径 = 纯查询：DU + 缺口 → 「下一步」
```

### 3.1 DeliveryUnit（DU）

一个需求/Bug 从分诊确认起创建的档案袋，持有：

| 字段 | 内容 |
|---|---|
| 目标 | 需求要干什么（源自 Issue 正文/草稿） |
| 产物清单 | 该出的东西：草稿、design.md、test-plan.md、发布计划、MR |
| 证据集 | 各环境执行证据、评审结论、验收记录（摘要 + 本地明细指针） |
| 资源集 | ResourceRegistry 登记项的引用 |
| 受影响维度 | 技术方案声明的维度集合（复用现有 7 维词汇：functional/api-contract/data-model/permission/frontend-route/schedule/release） |
| GateSet | 由维度推导并冻结的门禁单（见 3.2） |

**持久化**：DU 的对外可见部分 = 流转评论（含证据摘要）；DU 的完整执行明细 = 本地 `.glab-flow/<iid>/`（state + 证据明细）。两者不一致时以 GitLab 回读为准（沿用现有对账精神）。

### 3.2 GateSet（门禁单）

**机制**：声明式「维度 → 门禁」推导矩阵，进 state-machine.yaml，由引擎纯函数计算：

| 技术方案声明的受影响维度 | 推导出的门禁集 |
|---|---|
| 前端文案/UI（无路由/契约变化） | local 受影响 case + 代码走查；跳过「测试中」 |
| 局部行为（模块内） | local 闭环 + 提测部署；测试中只复核受影响 case |
| 接口契约（api-contract） | 契约同步 + local/test 双环境 + MR 评审 |
| 数据模型 / 权限 | 双环境 + MR 评审 + 全量回归 + 回滚预案 |
| 生产配置 / 合规（release） | 上述 + 发布检查升级 |

GateSet 决定四件事：**状态路径**（可跳过哪些状态）、**各环境执行范围**（全部/受影响 case）、**MR 评审与否**、**回归深度与回滚预案**。

**生命周期**：
1. 分诊时：不定路线（只确认类型 + Assignee）。
2. 待评审：评审证据积累影响维度，可显示「初步维度」，不绑定。
3. 技术方案：design.md 必须声明受影响维度（方案本该回答的问题）。
4. **已评审→开发中（绑定点）**：引擎从声明维度确定性推导 GateSet，与计划提测/上线日期**同一次 L2 批量确认**；人可增删门禁（显式改判），确认后冻结。
5. 实施中：实际改动触到未声明维度 → 变化闭环触发 GateSet 自动扩容（棘轮只升不降）；降级 = L2 显式改判留痕。

### 3.3 ActionPolicy（动作分层）

| 层 | 定义 | 例子 |
|---|---|---|
| L1 自动 | 可逆，**或**非生产环境的任何操作；执行后留审计 | 本地/test 环境一切执行、非生产凭据注入（test-config 路由自动取）、Apifox 资产增删、测试数据、分支/worktree、commit/push、代码评审、报告回读比对 |
| L2 判断 | 系统无法替人做的业务判断；**攒一批一次问** | 评审通过/退回、验收结论、GateSet 增删（改判）、提测/上线整体放行、外部事实导入确认 |
| L3 硬门 | 不可逆，恒人工，不可配置关闭 | 生产部署、关闭 Issue（终态原子：标签+Assignee+评论+close 同次） |

**划线原则**：凭据与环境操作按「是否生产」划线，不按「是否敏感」划线——非生产账号密码是测试数据，L1 直取直用。**评论写入归 L2**（G8 评论不可变，发了不能撤），L1 覆盖本地/分支/AI 分支内动作；MR 评审结论评论发到 MR（代码域），属 L1。

### 3.4 ResourceRegistry（资源登记表）

为 DU 创建的每项资源（分支、worktree、Apifox 场景/数据集/套件、AuthProfile 引用、测试数据、报告、部署版本）在创建时显式注册：

```yaml
# DU 资源登记项（示意）
- id: tmp-data-88-member-export
  kind: apifox-test-data
  scope: non-prod
  createdAt: ...
  lifecycle: temporary        # temporary | shared-candidate | permanent
  cleanupHint: 需求结束前清理或升级为共享资产
```

职责：创建校验（命名/归属/环境一致性）、引用检查（资源被哪些 case/套件引用）、**终态清理清单**（终态钩子自动生成，逐项处置：升级共享/删除/保留，处置按项 L1/L2）。

### 3.5 投影与对账

- **投影函数**：`DU 状态推导 × GateSet 状态路径 → labels`。对外 8 状态词汇表不变；R1 形态的 Issue 永远不会出现「测试中」标签。
- **对账（reconcile）**：人工在 GitLab 改 label 不再是「脏状态异常」而是「投影漂移」。`next` 检测到 labels 与 DU 事实不一致 → 列版本差 → 一次 L2 确认「以哪个为准」→ 更新 DU 或要求回改 label → 继续。人工发布/CI 结果同理：导入为 DU 事实。
- **存量接入**：旧 Issue 首次被新引擎读取时，回读全部 notes + labels 推导出 DU（状态、已达标门禁、资源），历史评论只读不迁移。

## 4. 流程设计（对外不变、对内新路）

### 4.1 需求（story）标准路线 — 7 次确认

```
①分诊（类型+Assignee）→ ②需求评审结论 → ③方案放行（日期+GateSet 同批确认）
→ ④提测放行（合并+构建+证据摘要，一次问）→ ⑤测试验收放行
→ ⑥生产部署（L3）→ ⑦产品验收+关闭（L3·终态原子）
```

中间执行（编码、自测、Apifox、资产、代码评审、测试执行、MR 评审、发布计划）全部 L1 自动，评论不进 Issue；终态后资源清理清单自动生成。

### 4.2 需求（story）简单路线 — 4 次确认

方案声明「只改文案/局部行为」→ GateSet 跳过「测试中」等状态 → `分诊 → 方案放行 → 提测 → 生产部署+关闭`。「本地通过直接上生产」= 此路线下的最短路径（生产部署仍 L3）。

### 4.3 变化分级闭环（任何阶段）

```
发现偏差 → cli change（带事实）→ 引擎定级（人可在 L2 批量确认改判）
  文案/UI      → 只重跑受影响 case；不动 plan-version；单快速关闭
  局部行为     → 局部回归 + 代码评审；受影响 case 重跑
  接口契约     → 契约同步 + 双环境重测 + MR 评审
  数据/权限    → 全量回归 + 发布检查 + 回滚预案 + 双环境重测
→ GateSet 自动扩容（棘轮）→ 补对应深度检查 → 关闭变更单 → 继续流转
```

open 变更单仍阻断正向流转（G16 语义保留），但轻量级的关闭证据要求随级别大幅减轻。

### 4.4 Bug 流 — 5 次确认

`①确认缺陷+Assignee → ②提测 → ③测试验收 → ④生产部署（L3）→ ⑤生产验证+关闭（L3）`。门禁集由根因分析触碰的维度推导（文案级 bug 与数据迁移 bug 走不同深度回归）。

## 5. Issue 信息分层

| 层 | 内容 | 位置 |
|---|---|---|
| 团队可见（交接） | 流转评论：状态头 + 内容体 + 证据摘要（计划版本/环境/关键结论 digest）；周排期区块（Harness 协议） | GitLab Issue |
| 代码域 | MR 评审结论评论 | 各 MR |
| 执行明细 | TestRun/AssetAudit 明细、变更单开闭明细、资源登记、取证过程 | 本地 `.glab-flow/<iid>/`（DU 派生） |

## 6. 引擎命令重构清单

| 现有命令 | 去向 |
|---|---|
| `transition` | 保留；输入增加 DU/GateSet，输出按 GateSet 决定跳状态与确认批量 |
| `change-impact` / `change-close` | 合并升级为 `change`：输入偏差事实 → 定级 + GateSet 扩容 + 按级别的关闭要求 |
| `validate` / `plan` / `render` / `plan-return` / `week-plan-change` / `config` / `state-*` / `progress` / `test-config` / `asset-audit` / `test-run` / `evidence` / `version` | 基本保留；校验规则从「固定每转换」改为「查 GateSet」 |
| —（新增） | `next`：最短路径查询（在哪/阻塞/最快下一步/谁欠什么/投影漂移提示） |
| —（新增） | `reconcile`：外部事实导入对账（手动部署/手动改标签/CI 结果 → DU 事实） |
| —（新增） | `resource`：资源登记/校验/清理清单生成 |

护栏 G1–G16 不删，改挂法：G14（MR 评审）只在 GateSet 含此项时生效；G11（阻塞全验证）只在进入过测试环境的路线生效；G15（需求评审取证）轻量路线可豁免；G3（hard_gate）恒生效。contract.ts 一致性校验同步改为覆盖维度→门禁矩阵。

## 7. 指标（衡量交付而非合规）

流程终态自动统计并写入 DU：人工确认次数（按层分）、从确认到交付周期、重复测试次数（同 case 同环境重跑）、环境阻塞次数与时长、人工介入时长、返工率（变更单触发回退比例）、资源清理完成率。

## 8. 分阶段实施（每阶段独立可用）

| 阶段 | 内容 | 验收感受 |
|---|---|---|
| 1 | ActionPolicy 落地：L1 放开非生产操作，确认改批量 | 标准需求确认 15+ → 7 |
| 2 | `next` 命令 + Issue 评论瘦身（评论只在流转时发） | Issue 干净、随时知道下一步 |
| 3 | GateSet + 维度推导 + 按需跳状态 | 简单需求不再陪跑重流程 |
| 4 | DU 主档 + ResourceRegistry + 终态清理清单 | 临时资源不再满天飞 |
| 5 | `change` 分级闭环 + `reconcile` 对账 | 改错不再全量回退；手动操作可导入 |
| 6 | 指标统计 | 周会看交付数字 |

每阶段完成后跑全量既有测试（contract/guard/transition 等），存量 Issue 以回读推导接入验证。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| 维度声明失真（方案说只改文案实际动了表） | 棘轮机制：实施中触发变化闭环自动扩容；漏报本身留痕为变更单 |
| 轻量路线误用（为省事全声明文案级） | 定级改判留痕 + 指标可见（返工率会暴露滥用）；MR 评审降级需显式确认 |
| DU 本地明细丢失（换机器/清目录） | 执行明细可从 GitLab 流转评论摘要 + Apifox/Jenkins 回读重建（派生缓存定位） |
| 与 Harness 周排期协议耦合 | 周排期区块协议不变，仍随流转评论追加；Milestone 同步意图保持 postWriteback |
| 一次性改动面过大 | 分 6 阶段，每阶段独立可用 + 全量回归 |
