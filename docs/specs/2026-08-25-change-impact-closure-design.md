# 需求与技术方案变更闭环设计

## 目标

需求、技术方案或实现发现的错误不能只修改局部文件后继续推进。每次变更都要留下不可修改的 Issue 回执，明确受影响产物、应回退的评审节点、各环境需重跑的验证；未闭环时，状态机不得继续正向流转。

## 方案

采用独立的纯引擎旁路命令，而不新增顶层状态：

1. `change-impact` 接收当前节点、变更来源、影响维度与当前测试计划，输出一条仅评论的 `WritePlan` 和确定性的影响矩阵。
2. 评论中的 `glab-flow:change-impact:v1` 标记以 `status: open` 记录变更编号、必须更新的产物、建议退回节点及变更前测试计划版本。
3. Leader 回读评论后，按输出修订 proposal/design/test-plan/Apifox 资产、排期或发布材料；需要回退时仍使用既有 `plan-return`，不由旁路命令暗改 Issue 状态。
4. `change-close` 只在全部必需项有完成证据后生成 `status: closed` 的不可变评论。若测试计划被影响，它要求新计划有效且版本严格高于变更前版本；因此旧 local/test TestRun 和 AssetAudit 会被既有版本门禁自动淘汰。
5. `transition` 与 `validate` 每次读取 notes 时检查所有未关闭变更。存在 open 记录即拒绝正向状态流转，直到对应 close 回执已回读。

## 影响推导

变更输入把影响维度写成 `functional`、`api-contract`、`data-model`、`permission`、`frontend-route`、`release`。引擎按维度推导最小必需动作：

- 功能、接口、数据、权限或页面路由：更新技术方案、测试计划、Apifox 资产与 local 重测；已经进入测试及以后时还需 test 重测。
- 需求来源的变更额外要求更新提案并建议退回 `待评审`；技术方案来源建议回到 `已评审`；实现/测试发现的问题建议回到 `开发中`。
- 发布影响要求重新完成发布检查。

## 节点内进度

测试计划属于开发，不属于测试执行。二级步骤调整为：

`技术方案 → 测试计划 → 编码实现 → 本地自测 → 代码评审`

测试中只负责在测试环境执行同一计划：

`用例执行 → 阻塞修复 → 复测`

## 边界与验证

引擎只解析、验证、推导和渲染，不执行 GitLab、修改本地产物或运行测试。Leader 继续负责预览确认、GitLab 写回回读、`plan-return`、Apifox/本地/测试环境执行。验证覆盖：变更影响推导、开闭回执解析、未闭环阻断、测试计划版本递增及二级节点契约。
