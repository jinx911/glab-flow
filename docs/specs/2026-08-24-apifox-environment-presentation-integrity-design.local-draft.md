# Apifox 多环境与页面展示一致性设计

## 背景与决策

glab-flow 已将 local 与 test 作为同一测试计划的两个执行环境，并要求以 Apifox 资产审计和 TestRun 作为状态门禁。本设计补齐一个此前缺失的产品契约：**用户在 Apifox 页面看到的场景、套件和数据集信息，也必须准确表达其用途和环境，不能与计划或真实执行证据相互矛盾。**

这不是仅靠标签改善可读性的工作。环境展示错误会使使用者把 local 的结果误判为 Stage 验收，或把跨环境流程误判为已覆盖全部环境，因此属于质量门禁问题。

本设计适用于 local、test（当前 OA 中为 Stage）与未来 production。生产环境沿用资产与证据模型，但默认只读，是否运行和是否接入状态门禁由后续明确授权的需求决定。

## 已验证的 Apifox 行为

以 OA Platform 项目 `8731182` 的 Issue #172 为例：

- `172-stage-验收聚合流程` 的步骤请求实际指向 `stage-oa`，描述也记录了 Stage 环境 ID；
- 场景 `get` 回读没有稳定、可校验的“默认运行环境”字段；
- 场景运行由命令显式传入 `--environment <environmentId>`；
- 测试报告回读包含 `environmentName`。Stage 套件报告 `25546373` 的 `environmentName` 为 `Stage`；
- 但 Apifox 场景列表仍可能显示“本地 tenant.oa.com”。

因此，列表“运行环境”列不能单独充当实际执行证据；其精确 UI 语义也不能由 CLI 猜测。它仍是用户可见的产品数据，必须被主动校验和修复。

## 环境事实模型

每一条测试资产或运行记录必须区分以下四种事实，禁止混用：

| 层次 | 事实源 | 用途 |
|---|---|---|
| 计划环境 | `test-plan.md` 的 `requiredEnvironments` 与环境 Profile | 定义此用例应在哪些环境验证 |
| 目标执行环境 | 本次 Apifox 命令的显式 environment ID | 防止运行时依赖默认环境 |
| 实际执行环境 | Apifox 测试报告的 `environmentName`、报告 ID 与统计 | 作为 TestRun 的外部执行证据 |
| 页面展示环境 | Apifox 资源列表/详情中可见的运行环境、名称、目录、标签、最近结果 | 保证使用者不会被 UI 误导 |

`test-config.md` 继续维护逻辑环境到项目、分支、environment ID、账号与数据前缀的映射。引擎只校验这些记录的确定性契约；Apifox CLI 调用和页面读取仍由 Leader 完成，不能进入引擎。

## 资产分层与复用

### 可复用基础资产

场景用例承载稳定业务步骤、断言、变量传递与清理。测试数据承载输入矩阵，测试套件或场景分组承载稳定的执行入口。它们优先按业务能力复用，不能因为新 Issue 或环境而无差别复制。

### 面向环境的验收入口

一个入口只有在用户能从 Apifox 界面准确判断其环境时，才能用于环境验收：

- 单环境入口必须在名称、目录、标签、执行命令、测试报告和列表展示上均指向同一环境；
- 同一流程仅环境、数据集或循环配置不同，优先使用 Apifox 场景实例保存运行配置，不复制流程步骤；
- 若当前项目 UI 无法让一个“多环境”入口准确表示多个环境，必须提供 `local`、`test` 等环境专属实例或轻量包装入口，并引用共享场景/单接口用例；
- 共享基线和模板资产必须归入明确的共享目录，标记 `baseline` 或 `template`，不得被写入环境验收 TestRun；
- 环境专属入口可在名称中带 `local` / `stage`，这是为消除 UI 歧义的例外；基础资产仍保持业务语义命名。

这避免了两个极端：既不复制整套步骤，也不保留一个页面显示“本地”、实际却被当作 Stage 或多环境验收的模糊入口。

## 认证作为共用测试能力

需要登录的接口不能要求每个业务接口或每个新需求重新处理认证。每个 Apifox 项目定义可复用的 `AuthProfile`；它不是明文凭据容器，而是一个可审计的登录契约：

```text
profile：client-user | hr-admin | supplier-admin
owner：持有登录接口的 Apifox 项目与场景
environment binding：local / test / production 的 environment ID 与运行变量入口
credential reference：本机安全凭据引用，不进入 Apifox、GitLab 评论或报告正文
bootstrap：登录步骤、成功断言、token JSONPath 与目标临时变量名
injection：公共 Auth/Header 配置，例如 Bearer {{auth_token}}
scope：允许调用的业务域、角色与套件
teardown：可选退出登录；与业务测试数据清理分离
```

执行时由运行时 `--variables` 文件按 environment ID 注入账号、密码和环境专属参数；不依赖 CLI 的默认环境值，也不把敏感值持久化到场景、项目变量、Issue 或报告。token 必须在登录接口的后置操作中同时完成“登录成功 + token 存在”断言和变量提取，并存入**本次场景运行有效的临时变量**。后续业务接口只引用统一的鉴权变量，例如 `Bearer {{auth_token}}`。

对同一场景内的紧邻步骤，允许使用前序步骤动态引用；但作为可复用契约时，优先使用命名临时变量，避免下游依赖脆弱的步骤序号。跨场景或跨套件运行时，只有在登录引导位于执行链路首部且显式启用运行时变量传递时，才可复用该 token；否则每个独立入口在开头重新登录。

认证失败不能被静默重试掩盖：场景开头应获取新 token；中途 401/403 必须保留为失败证据，除非测试计划明确覆盖“刷新 token 后重试”的业务行为。退出登录仅在系统确有会话释放要求时在整个场景末尾运行一次；测试数据删除、回滚和 fixture 清理是独立的 teardown，不得混入登录后置操作。

现有 #172 场景虽以首步登录并直接引用 `{{$.1.response.body.data.token}}` 完成后续请求，但尚未统一为 `AuthProfile` 的后置提取与共享变量契约。迁移时应保留其登录成功断言，将直接步骤引用收敛为临时 token 变量，并用本节的审计规则回读验证。

## 页面展示一致性门禁

新增 `ApifoxPresentationAudit`，作为资产审计的扩展而非对 TestRun 的替代。每个新增、更新或作为本次执行入口的资产都要具有预期投影与回读投影：

```text
资源身份：project / branch / type / id
计划归属：test-plan 版本 / case ID / 逻辑环境
预期展示：名称 / 目录 / 优先级 / 标签 / 页面运行环境
实际展示：上述页面回读值 / 最近运行结果
实际运行：explicit environment ID / report ID / report.environmentName
结论：passed | mismatch | unavailable
```

规则如下：

1. 单环境入口的“页面运行环境”必须等于计划环境，且最近运行报告也必须属于该环境。
2. 跨环境基础资产不直接充当环境验收入口；若其页面展示无法表达多环境意图，审计必须标为 `mismatch`，直到改用环境实例/包装入口。
3. 测试数据必须显示其业务用途、环境范围、数据前缀和归属资产；不得将 local、Stage 或生产数据混在无法区分的数据集中。
4. 套件/场景分组必须显示稳定执行目的及成员；空集合、环境混杂但无说明、或成员与计划入口不一致均为失败。
5. 需要认证的入口必须引用存在的 AuthProfile；登录步骤、临时 token 提取、统一鉴权变量与计划角色均可回读，且没有明文凭据或持久 token。
6. 页面无法读取、Apifox 不提供所需字段或字段语义无法确认时，结论只能是 `unavailable`，不能伪造通过。

在实现上，现有 `glab-flow:apifox-asset-audit:v1` 保持兼容；新能力使用版本化的 `v2` 评论块或等价的显式扩展字段。只有计划声明为需要页面展示审计的资产才强制 v2，避免历史资产在未迁移前被静默误判为通过。

## 执行、回读与写回顺序

对每个环境依次执行：

```text
读取 TestPlan
  → 盘点既有 Apifox 资产
  → 选择复用基础资产和环境入口
  → schema 校验后受控写入（需要写入时）
  → CLI list/get 回读结构
  → 显式指定环境运行
  → 回读报告的 environmentName、统计与详情
  → 在 Apifox 页面核对列表/详情投影
  → 写入 AssetAudit + PresentationAudit
  → 回读 GitLab Issue
  → 写入同版本 TestRun
```

运行必须显式传入 `--environment <id>`；不允许依赖 UI 当前选择或 CLI 默认值。报告上传、外部 AI 写入权限和终端提升权限仍按既有授权预检执行，拒绝后停止而非删掉报告上传参数降级。

页面核对采用两层证据：先以 CLI `list/get` 验证资源身份、目录、名称、标签、成员与数据；再用 Apifox 页面列表/详情验证用户实际看到的投影。后者可由受控浏览器读取或人工复核完成，必须在审计中记录资源链接、核对时间和结论。

## 与流程门禁的关系

- `local` TestRun 继续是“开发中 → 测试中”的前置；`test` TestRun 继续是“测试中 → 待发布”的前置。
- 每个 TestRun 必须引用同计划版本、同逻辑环境且通过的资产审计；需要页面展示审计的资产还必须有通过的 PresentationAudit。
- `mismatch`、`unavailable`、环境不一致、报告环境缺失、数据混用、空资产或未处置临时数据，均阻断对应环境的 TestRun 和状态推进。
- 代码单测、静态检查、构建与评审是必要的实现验证，但不能替代任何环境的 TestRun 或页面展示一致性审计。

## 迁移与首个样板

OA Platform 的 Issue #172 是首个迁移样板：

1. 盘点 14 个场景、现有目录、套件、数据集和报告；
2. 把 Stage 和 local 的验收入口与共享基线分开；对跨环境流程优先建立引用共享步骤的环境实例/包装入口；
3. 将首步登录升级为可复用 AuthProfile：后置提取临时 token、统一注入鉴权头，并在完整场景和套件链路中验证变量传递；
4. 使用 Stage 和 local 分别显式运行并回读报告；
5. 修正 Apifox 列表中“运行环境”、名称、目录、标签与最近结果的可见投影；
6. 产出 v2 审计，确认截图中类似“stage 场景显示本地”的情况无法再通过门禁。

不自动删除现有资产、不批量改写全部历史项目，也不假定每个项目都具备相同的套件/场景实例能力。发现能力差异时，应停止在可审计的 `unavailable` 状态并给出迁移建议。

## 验收标准

1. 每个环境验收入口的计划、实际运行报告与 Apifox 页面展示一致。
2. 任何 Stage/test 入口在页面显示 local，或反向情况，都会被审计发现并阻断通过。
3. 跨环境流程通过共享基础资产加环境入口复用，不复制完整步骤，也不留下含糊的“多环境”验收入口。
4. 需要认证的业务接口使用 AuthProfile，不复制登录逻辑、不持久化凭据/token，并能在跨场景链路中验证 token 传递。
5. 新旧审计评论可版本化共存；历史资产不会被静默视作 v2 通过。
6. 本地、测试和未来生产使用同一模型，仅因 Profile、授权和状态门禁配置不同。
