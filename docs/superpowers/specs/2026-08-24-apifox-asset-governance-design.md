# Apifox 自动化测试资产治理设计

## 目标

随着需求增加，Apifox 的场景用例、测试套件/场景分组和测试数据必须沉淀为可复用的测试资产，而不是按 Issue 无序叠加。本设计在不让 glab-flow 直接读写 Apifox 的前提下，建立可审计的资产治理契约，并让它与已经定义的 local/test TestRun 门禁一致。

## 官方能力与边界

- Apifox 将自动化测试的业务流程承载在**场景用例**中；场景可导入接口/用例并以流程控制组件编排。[自动化测试](https://docs.apifox.com/automated-testing)
- 同一流程仅运行环境、数据集或循环配置不同时，使用**场景实例**保存运行配置，不复制步骤。[保存为场景实例](https://apifox.com/help/automated-testing/test-scenarios/save-as-testing-cases)
- **测试数据**是可云端同步、按环境配置的二维数据集；列名对应变量，每行是一轮执行输入。[数据驱动测试](https://docs.apifox.com/data-driven-testing)
- 当前官方文档对**测试套件**存在版本差异：新版将它定位为场景/单接口用例的聚合执行入口，适合冒烟、回归和巡检；旧帮助中心称该能力已迁移至场景分组。因此运行时必须以当前项目 UI、CLI `--help` 和可回读资源为准，不能把“必须使用测试套件”写死。[新版套件文档](https://docs.apifox.com/7927162m0) [旧版迁移说明](https://apifox.com/help/app/test-manage/test-suite/)

官方没有定义固定目录层级；下列命名、生命周期与审计规则是 glab-flow 在官方资源模型上的团队治理补充。

## 资产模型

| 资产 | 唯一职责 | 可复用范围 | 禁止事项 |
|---|---|---|---|
| 场景用例 | 承载一个稳定、可理解的业务流程及其断言、变量传递、清理 | 同一业务能力的多次需求与回归 | 因 Issue 或环境复制同一流程；创建无步骤空场景 |
| 测试套件或场景分组 | 聚合稳定执行目标：提交冒烟、模块回归、发布回归、定期巡检 | 多个需求共享 | 每个 Issue 新建一套；创建空集合；用环境名复制同成员集合 |
| 测试数据 | 承载变化的输入、边界矩阵与环境差异；不承载流程逻辑 | 同能力/场景，按环境分值 | 将测试数据硬编码进场景；创建无数据行的数据集；用生产真实敏感数据填充 local/test |
| 场景实例 | 保存同一场景的运行配置（环境、数据集、循环次数） | 同一业务流程的不同运行上下文 | 为仅配置不同的情况复制场景步骤 |

## 目录、命名与复用规则

每个项目内分别按资源目录支持情况组织，但逻辑层级一致：

```text
自动化测试
├── <业务域>
│   ├── <功能能力>
│   │   ├── 场景：<能力>-主流程
│   │   ├── 场景：<能力>-异常与权限
│   │   └── 数据：<能力>-边界矩阵
├── 回归入口
│   ├── 冒烟-核心流程
│   ├── 回归-<业务域>
│   └── 发布-全量回归
└── 临时数据
    └── TMP-<iid>-<用途>
```

1. 新需求开始时，先按业务域、能力、接口和现有场景检索；能复用则更新或引用，不能复用才新建。
2. 名称表达业务能力和测试意图，不携带环境名、个人名或临时 Issue 编号；环境差异通过环境 Profile、测试数据或场景实例表达。
3. 套件可用时，只按稳定执行目的建立；当前实例不支持套件时，用同名场景分组与批量执行实现相同入口，不降低治理要求。
4. 临时数据必须以 `TMP-<iid>-` 开头，登记创建原因、清理时点和清理结果；在需求结束前删除或明确升级为共享资产。
5. 若同一流程的步骤复用不足以支撑需求差异，优先导入已有接口/单接口用例或引用既有场景；仅当业务步骤或断言确有差异时创建新场景。

## 需求级资产清单与审计

`test-plan.md` 增加“Apifox 资产清单”章节。每项包含：

- `type`：`scenario` / `suite-or-group` / `test-data` / `scenario-instance`；
- `id`、项目、分支、目录路径和名称；
- `action`：`reuse` / `create` / `update` / `retire` / `cleanup`；
- 对应测试计划 case、环境和运行入口；
- 复用依据或新建理由；临时数据还需清理时点。

每个环境执行前，Leader 使用当前 Apifox CLI 的 `list/get`（及需要时 `test-data`、`test-suite`/场景分组命令）回读资产。创建或更新时遵循：先读已有资产 → 获取当前 schema → 校验 → 写入 → `get` 回读；命令与资源类型以当前 CLI `--help` 为准。

审计至少确认：

1. 每个场景的步骤非空，引用/导入关系可回读；
2. 可用套件或场景分组的成员非空，并对应计划指定的执行入口；
3. 数据集存在实际数据行，变量列与场景引用一致，环境值不串用；
4. 本需求没有创建未处置的重复资产、孤儿资产或过期临时数据；
5. 新建资产已归入目标目录，复用/新增判断及清理结果可追溯。

## 门禁与证据

引入单独的不可变 Issue 评论 `glab-flow:apifox-asset-audit:v1`。它记录：计划版本、目标项目/分支、审计环境、逐类资产清单、回读命令/链接、结果与未处置问题数。

- local TestRun 必须关联同计划版本、已通过的 local 资产审计；
- test TestRun 必须关联同计划版本、已通过的 test 资产审计；
- 审计缺失、marker 无效、资源为空、未处置重复/孤儿/临时数据，均不能形成 TestRun，因而阻断对应流转；
- 引擎只解析和校验评论/计划一致性；Apifox 查询与写入继续由 Leader 在明确授权下通过 CLI 执行。

## 错误处理与非目标

- Apifox 权限、CLI 版本或套件能力不可用时停止审计，报告缺口；不可伪造审计通过，也不可假定所有项目都支持测试套件。
- 本次不自动删除任何已有 Apifox 资产；清理是人工确认后的受控写操作。
- 本次不建设跨项目的全局资产数据库、不做语义级自动重复判断，也不把生产环境纳入测试门禁。

## 验收标准

1. 活跃 glab-flow 文档明确四类资产职责、复用优先、环境配置不复制场景和临时数据生命周期。
2. 引擎能拒绝缺失、版本不匹配或存在未处置问题的资产审计。
3. TestRun 与资产审计、测试计划版本和环境三者可确定性关联。
4. 流程契约测试覆盖套件能力发现、审计门禁、临时数据和无静默降级规则。
