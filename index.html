GitLab 原生交付 Harness

让 AI 推进需求，
不绕过交付流程。

glab-flow 将 GitLab Issue 驱动的需求交付做成确定性闭环：人负责判断与确认，纯引擎负责节点、护栏、证据、回退和可恢复的写回计划。

01

GitLab Issue 是事实源标签与不可变评论可回读；本地状态仅是恢复缓存。

02

引擎零副作用只计算、校验、渲染和建计划；Leader 才使用已认证的 glab 写回。

03

一份计划，多环境执行local 与 test 使用同一份版本化测试计划，环境只改变配置。

04

变更必须闭环需求、方案或实现改变会使相关证据失效，未关闭影响单不能继续流转。

交付流程

一条需求，从澄清到验收的完整路线。

主线是 Story 状态机；每一个箭头都代表有证据、有负责人、可预览的转换。Bug 进入“已确认缺陷”后复用开发、测试、发布与生产验证闭环。

常规可计算转换人工 hard gate变更回退与闭环流程图表达 Story 主线；Bug 从“已确认缺陷”进入同一开发、测试、发布与生产验证闭环。

评审先把问题问透

图片必须 OCR；前端位置须由代码路由验证；关键不确定性进入决策账本。

测试计划先于编码

开发中先设计计划，再编码和本地完整业务闭环；测试环境执行同一计划。

快速开始

从 GitLab Issue 开始，不从一段孤立的提示词开始。

01
安装并初始化项目上下文

将技能链接到 Claude Code / Codex，为目标工作区生成流程与测试配置。

02
以 Issue 触发完整流转

引擎读取标签与评论，计算当前节点、缺口、回写计划和节点内进度。

03
在每个门禁处取得证据

需求评审、技术方案、本地闭环、测试环境、MR 与发布均有独立职责和证据。

04
用不可变回执恢复与审计

写回失败或跨会话时从 GitLab 回读，只重试第一个未完成阶段。
